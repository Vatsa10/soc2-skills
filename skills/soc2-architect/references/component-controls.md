# Component to Control Map

> This skill prepares for a SOC 2 audit; it is not an attestation. Only a licensed CPA firm can issue a SOC 2 Type 1 or Type 2 report.

Use this table to map each system component to the controls it must satisfy. Control IDs are defined in `../../soc2/references/control-catalog.md` (one-line index: `../../soc2/references/control-index.md`; read the index first and open a full entry only by searching `### <ID>`). Never copy a TSC mapping from this file: always take it from the catalog entry's `TSC:` line.

Service names here are examples that satisfy the control, not the only acceptable choice. For the full AWS | GCP | Azure service list per control family (current, verified names) use `../../soc2/references/cloud-equivalents.md`; the columns below are the short form. Each is chosen so it can emit machine-readable evidence (the Type 2 requirement).

Service names verified current as of 2026-10: Google Security Operations (Google SecOps, formerly Chronicle); Knowledge Catalog (formerly Dataplex Universal Catalog, renamed 2026-04-10; API and IAM names unchanged); BigQuery policy tags via Policy Tag Manager (Data Catalog search/metadata APIs were discontinued 2026-06-01, policy tags were not); AWS Security Hub CSPM (posture checks; "AWS Security Hub" is now a separate aggregation service); Iru (formerly Kandji); Opsgenie is end-of-sale and reaches end of support 2027-04-05, so prefer PagerDuty or Jira Service Management; Trivy config replaces tfsec (tfsec gets no new checks).

## Cross-cutting controls (apply to every design)

These apply regardless of component. Add them once to the architecture, not per component. Every GOV, RSK, MON and CTL control belongs here, so none is left unmapped.

| Area | Control IDs |
|---|---|
| Governance and system description | GOV-03, GOV-04, GOV-07, GOV-08, GOV-09, GOV-10, GOV-13, CTL-01, CTL-04 |
| Subservice organizations and customer commitments | GOV-11 (carve-out vs inclusive for each hosting/sub-processor), GOV-12 (CUECs communicated to customers) |
| Risk | RSK-01, RSK-02, RSK-03, RSK-04 |
| Monitoring of controls | MON-01, MON-02 (annual third-party penetration test), MON-03, MON-04 |
| People | GOV-01, GOV-02, GOV-05, GOV-06, CF-05 |
| Segregation and baselines | CTL-02, CTL-03 |

If GOV-03, GOV-06, GOV-09, GOV-10, MON-02, MON-04 or RSK-03 are not realistic for the company size, list them under `Excluded` with the reason in the architecture document instead of dropping silently.

## Data-class triggers

| If the system handles | Add these controls | Note |
|---|---|---|
| Any personal information | PR-01 through PR-17 (select per catalog `Applies when`), CF-01 | Privacy TSC must be in scope for PR controls to be examined. If the user excluded privacy, flag it once (see the SKILL's scope-gap rule) |
| Sensitive personal information (health, financial, government ID, children) | PR-04, CF-02, AC-09, AC-10 | Explicit consent and tighter access. Data minimisation first: see below |
| Government identifiers (SSN, national ID, passport) | AC-09 (field-level encryption), CF-02, PR-03, PR-06 | Challenge whether the number must be stored at all: tokenize through a vendor (a vault or payment/identity provider holds the real value and the system keeps a token), or store last-4 only; if the full value is unavoidable, field-level encryption with a dedicated key, no logging of the value, masked in UIs, shortest retention |
| Cardholder data | Flag to the user that PCI DSS applies separately; keep CDE segmentation (AC-12) and encryption (AC-09, AC-10). Prefer a hosted payment page or tokenization so card numbers never reach the system | SOC 2 does not replace PCI DSS |
| Protected health information | Flag to the user that HIPAA applies separately; add business associate terms (VND-04) | SOC 2 does not replace HIPAA |
| Multi-tenant customer data | AC-06, AC-12, CF-02, PI-05 | Tenant isolation must be designed and testable (cross-tenant access test in CI) |
| Customer-supplied confidential data | CF-01, CF-02, CF-03, CF-04, CF-06 | Confidentiality TSC |
| Financial or transactional processing (invoices, payments, billing) | PI-01 through PI-07 | Processing Integrity: idempotency (PI-06), rounding rules and totals reconciliation (PI-02, PI-03), timeliness SLA (PI-07) |

## Notes for the model

- A component may match several rows (for example a managed Postgres holding PII matches Databases and PII stores). Merge the control lists and deduplicate.
- If a component has no row, treat it as the nearest type, then state the assumption in the architecture document.
- If the user is on a cloud not listed (for example on-premises, Oracle, Cloudflare), keep the control IDs and propose equivalent services; mark them as "equivalent, confirm with auditor".
- Physical security (AC-13) and environmental controls (AV-06) are inherited from the hosting provider. Record them as inherited, record the provider under GOV-11 (carve-out method), and note that the provider's SOC 2 report must be collected and reviewed under VND-03, with its CUECs mapped to your own controls.
- Scope filter: drop controls whose TSC lines fall only in categories the user excluded. Security (CC) controls are always in scope.
- Unmapped-control diff: after mapping, list every ID in `control-index.md` that appears nowhere in the design. Each must be either added or listed under `Excluded` with a one-line reason. This file is a convenience; the index is the source of truth, and new catalog controls take precedence over this table.
